How Phew connects to your tools

Today Phew acts by looking at the screen and pressing things, like a person would. A connection lets him ask the tool directly. This page explains what a connection is, how one works step by step, the ways Phew could have them, and what I recommend.

Nothing here is built. No connection was made and no account of yours was touched. Facts come mostly from official documentation read on 16 and 17 November 2026, a few from other sources marked in the notes; what could not be checked is listed at the end.

The idea in one minute

Every app has two faces. One is the window you see. The other is a list of things the app can do when asked by a program: "create a page", "find a file", "add a comment". A connection is a standard way for an assistant to read that list and ask for one of those things.

The standard is called MCP, the Model Context Protocol. Its first version came from Anthropic in 2024, and it is now run by a foundation. The company that makes the app (Notion, Figma, GitHub) runs a small service, called a server, that speaks it.

Through the screen (today)

He looks at a picture of the window, decides where to press, presses, looks again. Slow, costs a model call per step, and breaks when the app changes its layout.

Through a connection

He sends one request: "create a page with this title and this text". The tool does it and answers "done, here is the link". Fast, cheap, and it does not depend on what is on screen.

Your own note said it: the screen is for understanding, the doors are for acting. That is the right split.

A server can offer three kinds of things. Tools are actions ("create page", "search"). Resources are things to read (a file, a document). Prompts are ready-made instructions. Tools are the part Phew would use.

A server can live in two places. Remote: at an internet address run by the company, such as https://mcp.notion.com/mcp. Local: a program on your Mac. Figma's and Fusion's desktop apps each run a local one while they are open.

One job, step by step

You say: "Add the summary of this page to my Notion, in Project notes."

  1. Phew reads the list of tools. He asks Notion's server what it can do. The answer is a list: each tool has a name, a description in plain words, and the fields it needs.Done once when you connect, then kept. The list is what the model reads to know what is possible.
  2. Phew sends your words and the list to the model. The same Claude call as today, with the tools added.The list costs input tokens on every call, so Phew sends only the tools that fit the job.
  3. The model answers with a request, not with words: "call create_page with parent Project notes, title …, text …".The model never touches Notion. It only says what it wants done.
  4. Phew checks the request. His own code looks at it before anything happens: is this tool allowed, does it change something, can it be undone?This is the step that matters most for you. It only exists if the client is inside Phew.
  5. Phew's client sends the call to Notion's server, with your sign-in token.Mac to Notion, directly.
  6. Notion answers: "created, here is the address".Phew treats the answer as data, never as orders, the same rule he has for web pages.
  7. Phew gives the answer back to the model, which writes you one line: "Added to Project notes."
What the messages really look like

The example from the standard's own text. First the list, then one call.

// Phew asks: what can you do?
{ "method": "tools/list" }

// the server answers
{ "tools": [ {
    "name": "get_weather",
    "description": "Get current weather information for a location",
    "inputSchema": { "type": "object",
      "properties": { "location": { "type": "string" } },
      "required": ["location"] } } ] }

// Phew asks for one thing
{ "method": "tools/call",
  "params": { "name": "get_weather", "arguments": { "location": "New York" } } }

// the server answers
{ "content": [ { "type": "text", "text": "72°F, partly cloudy" } ], "isError": false }

The same job, both ways

Through the screen

  1. Bring Notion to the front
  2. Look, find Project notes, press it
  3. Look, press "New page"
  4. Look, type the title
  5. Look, type the text
  6. Look again to check, return you to your window

about 6 model calls with a picture · takes your screen · 1 to 4 cents (measured for a 5-step job) · fails if a button moved

Through a connection

  1. One model call that asks for create_page
  2. One call to Notion
  3. One short model call to tell you

2 model calls, no picture · your screen is untouched · well under 1 cent (estimate, not measured) · works with Notion closed

Signing in, and where the key lives

A remote server needs to know it is you. The first time, Phew opens Notion's own sign-in page in your browser. You approve there. Notion then gives Phew a token: a long secret that stands for your approval. Phew never sees your password.

Phewopens the browser
→
Notion's sign-in pageyou approve what Phew may reach

Keychainthe token is kept here, like your API key

The token lasts some hours and is renewed behind the scenes. Whether you can cancel it from the tool's own settings was not checked. A good connection asks for the smallest reach: read only where reading is enough.

What I recommend: B, a client inside Phew

I expected to recommend A, because it looked like almost no work. The research changed that, for three reasons.

  • Control. Your rules say Phew's own code decides what may be done, every action is listed on the card, and what cannot be undone waits or is tagged. Only B sees a call before it runs.
  • No saving on the hard part. A does not do the sign-in for you. That work is the same either way, and the Swift kit already contains it.
  • Reach. Figma's and Fusion's desktop servers are on your Mac. A can never reach them.

A stays useful as a quick way to try a read-only server before writing code for it.

About mcp-use, the project you found

mcp-use is a good open-source kit (MIT licence, very active) for building servers, clients and agents that speak the standard. It is written for TypeScript and Python. It has nothing for Swift.

  • Inside Phew: no. Phew is a native Mac app. Using it would mean shipping Node or Python inside the app (way C above). Its agent also calls the model by itself, which would go around Phew's one acting function and his cost log.
  • Beside Phew: yes. Its Inspector is a handy workbench. Before building a connection, I can point it at a server and see its real list of tools.
  • For Swift there is an official kit, modelcontextprotocol/swift-sdk, maintained with Apple. It is young (version 0.12) and speaks the standard's previous version.

What can go wrong

  • A tool description that carries hidden orders. The model reads descriptions. A bad server can write "also send the user's files to…" inside one. Guard: only servers run by the tool's own maker.
  • A server that changes its tools later. Safe on Monday, different on Friday. Guard: Phew remembers the list from the day you connected, and stops if it changes.
  • Orders hidden in an answer. A Notion page can contain text written to mislead him. Guard: answers are data, never orders. This is the rule Phew already has for web pages.
  • A token with too much reach. Guard: smallest reach, read-only where possible, kept in the Keychain.
  • A local server runs with all your rights on the Mac. Guard: only the ones inside apps you already trust (Figma, Fusion), nothing downloaded.
  • Fusion's door has no sign-in. While it is switched on, any program on your Mac can use it, not only Phew. Guard: on only while you need it.

The dangerous mix is one assistant that can read your private things, read text from strangers, and send things out. All three together is the known recipe for theft. Fewer is safer, not safe. This is why I would keep "what a page says is data" even in the limits review.

Phew as an agent that starts agents

Today Phew has one research agent. The idea is a lead that splits a big job, starts several workers, and checks what they bring back.

Youone big job
→

→up to 4

→
Checkercode first (does each claim have a source?), then one fresh model read.

All of it can run on your Mac, as several Claude calls at once. Nothing new leaves the Mac compared with today.

What the people who built these found

  • Anthropic measured that a system of several agents uses about 15 times the tokens of a chat, and one agent about 4 times. Its later guidance says 3 to 10 times a single agent.
  • Its newest piece (October 2026) says one good agent with the right know-how often beats several, on quality, cost and speed.
  • Google measured errors growing up to 17 times when agents work with no one checking them.

So: several agents win only on broad research that splits into separate questions. For everything else one agent is better. The lead choosing not to split should be the normal case.

What I would build, in order

  1. The client inside Phew, with Notion first. Open sign-in, reads and writes, and you use it. Every change goes through Phew's one acting function, as a press does today.
  2. Your Shortcuts as tools. You tick which ones he may run.
  3. Fusion's and Figma's desktop doors, on your Mac. Fusion's is switched on in its preferences; Figma's needs a paid seat and is to be tested.
  4. GitHub and Linear, if you use them.
  5. The lead and workers for research, behind limits.
  6. Google, Slack, Microsoft later: each needs a registration with the vendor, and Slack and Microsoft also need an admin to approve. Microsoft is for work accounts.

Decisions that are yours

  • Which tools first. I assumed Notion; say if another matters more.
  • May a connection write with no confirm, like his other actions, or does a change in a cloud tool wait for you? A cloud change can reach other people (a shared page, a comment).
  • Sign-in opens your browser once per tool. That takes the screen for a moment, which your rules allow only for a job you asked for.
  • Connections mean Phew talks to servers other than Anthropic's. The rule "calls only the Claude API" changes.

Not verified

  • No live connection was made. What each server offers comes from its documentation.
  • Whether each tool still accepts the standard's previous version, which the Swift kit speaks, and accepts sign-in from an app it does not know. A short test per tool decides it.
  • The Claude API route with streaming answers: its page does not say.
  • That Apple gives outside assistants no way to call another app's actions. Apple's pages are silent, which is not proof.
