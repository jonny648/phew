1. Git and GitHub are two different things

Git is a program on your Mac. It records the history of a folder. Each time you say "save this state", it stores a snapshot called a commit, with a message, a date and an author. You can go back to any snapshot, compare two of them, or try an idea on the side without touching the main line.

GitHub is a website that hosts a copy of that history online, and adds tools around it: a page to read the code, discussions, task lists, automatic checks, and a place to publish finished versions for download.

Phew already uses Git: the project folder holds about 20 commits, one per finished piece of work. It does not use GitHub yet. Today the history exists only on your Mac.

Git is the notebook. GitHub is the shared shelf where a copy of the notebook is kept, with a reading room around it.

GitHub is the best known host. GitLab and Bitbucket do the same job. All of them speak Git.

2. Why people use it

  • History. Every change is recorded with its reason. When something breaks, you can see what changed and go back.
  • Backup. A second copy outside your Mac. If the disk dies, nothing is lost.
  • Working together. Several people change the same project without overwriting each other. Each change is proposed, read, then merged.
  • Trust. Users and employers can read the code, the history and how problems were handled. For open source it is the main proof that software does what it says.
  • Automation. At every change GitHub can build the app and run the tests on its own machines, and tell you if something broke.
  • Distribution. A finished version can be published on the project's page as a download.

4. How an app gets onto GitHub

  1. Clean first. Check that no password, API key or personal file is in the folder or in any past commit. History is pushed too: a key deleted last week is still in last week's commit.
  2. Tell Git what to ignore. A file named .gitignore lists what never goes in: build output, personal editor settings, system files.
  3. Create the repository on GitHub. Choose a name, and private or public.
  4. Connect and push. The local folder is told where its online copy lives, then every commit is sent.
  5. Switch on the automatic checks. A small file in .github/workflows/ tells GitHub to build and test at each push.
  6. From then on: commit, push. When a version is ready: tag it and publish a release.
# what steps 3 and 4 look like in the terminal
gh repo create phew --private --source=. --push

For Phew this is roadmap phase PG, at the end of the MVP. Claude Code runs the commands; you approve the push.

What never goes in

  • Secrets: API keys, passwords, signing certificates. Phew keeps its key in the Keychain for this reason.
  • Build output: the compiled app and Xcode's working files. They are large and can be rebuilt from the source.
  • Personal files: editor settings, .DS_Store, anything with your data or a real user's data.
  • Large binaries: videos, datasets, installers. They belong in a release or elsewhere.

What the finished app is

Phew.app looks like one file and is a folder (a "bundle"). Inside: the program itself, an Info.plist with its name, version and identifier, its icon and other resources, and a signature that proves who built it and that nothing was changed since.

7. What makes a project "professional"

There is no official rating. People judge a repository in the first minute by these signs:

  1. The README tells a stranger what it is, shows it, and gets them running in a few steps.
  2. A fresh download builds with one documented command, on a machine that is not yours.
  3. Tests exist and a green check shows they passed on the latest commit.
  4. Commits are small, with messages that say what changed and why.
  5. Versions are tagged, and a change log says what each one brought.
  6. There is a licence.
  7. No secrets, no personal data, no build output, no leftover files.
  8. The folders are named for what they hold, and nothing important hides in an odd place.
  9. Releases are signed, and installing does not trigger a security warning.
  10. Problems are tracked in the open and answered.

Points 1 to 8 are roadmap phase PG. Point 9 needs the paid Apple programme and is item L8. Point 10 starts when there are users.

8. How software reaches users

The code on GitHub is for developers. Users need the built app. The usual routes for a Mac app:

RouteHow it worksFor Phew
GitHub ReleasesThe built app, zipped or as a disk image (.dmg), attached to a version page. Users download and drag it to ApplicationsThe natural first route
Own websiteThe same file behind a download buttonLater, with the dashboard
HomebrewA catalogue used by technical users: brew install --cask name downloads the same filePossible once releases exist
Automatic updatesThe app checks a small file online and updates itself. Sparkle is the common open source toolNeeded as soon as other people use it
Mac App StoreApple reviews, hosts and updates the app, and takes a share of salesNot possible as built: the Store requires the App Sandbox, and Phew must read other apps' windows

Signing and notarization

macOS blocks apps from unknown sources. To open without a warning, an app distributed outside the Store must be:

  1. Signed with a "Developer ID" certificate, which ties it to an identified developer.
  2. Notarized: sent to Apple, whose service scans it automatically and returns a ticket. The ticket is attached to the app.

Both need membership of the Apple Developer Program, a yearly fee (99 US dollars a year when last checked; confirm on Apple's page). Phew is signed today with your free personal team, which is enough for your own Mac. On anyone else's Mac it would show a warning. That is roadmap item L8.

9. Versions and change logs

The common scheme is three numbers, MAJOR.MINOR.PATCH:

  • PATCH (0.1.0 to 0.1.1): fixes only.
  • MINOR (0.1.1 to 0.2.0): new features, nothing breaks.
  • MAJOR (0.9 to 1.0, 1.4 to 2.0): a big change, or something stops working the old way.

Anything starting with 0 says "still early, expect changes". Phew's MVP would be 0.1.0, tagged in Git as v0.1.0.

The change log is written for people, newest first: for each version, what was added, changed and fixed. Commit messages are for developers; the change log is for users.

10. Private, public, and your two-repository idea

PrivatePublic
Who can see itYou, and people you inviteEveryone
Good forBackup, history, work in progress, business plansOpen source, trust, a portfolio, getting help
NeedsNothing moreA licence, a clean history, a README for strangers
Automatic checksA monthly free allowance, then paid. Mac machines cost about ten times Linux onesFree on standard machines

Your decision: private now, pushed at the end of the MVP. Later, a second, public repository with only what is needed to build the app.

That split is a known pattern. How it would look:

  • Private repository: everything, as today. Plan, business targets, decisions, roadmap, and the code.
  • Public repository: Phew/, PhewTests/, Phew.xcodeproj, a README for strangers, a licence, the change log. No docs/, no roadmap, no role files.
  • History: the public one starts fresh, with one first commit, so the private history is not exposed.
  • Cost: two places to keep in step. A small script copies the code across at each release.
  • Before going public: the project settings contain your Apple team number and an app identifier with your name in it. Neither is a secret, and both are personal. Decide then whether to change them.

Automatic checks while private: GitHub's free plan includes 12 US dollars of machine time a month, and a Mac machine costs about 6 cents a minute. A Phew build with tests takes a few minutes, so roughly 50 checked pushes a month fit before anything is charged.
