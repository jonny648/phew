PHEW · THE LANGUAGE QUESTION · 17 NOVEMBER 2026

Swift, or TypeScript for the thinking part?

You asked whether Phew's agents should move to TypeScript, with Swift kept only for the Mac app, to reach more capabilities. This page gives the answer, the reasons, and the numbers from a small trial.

The answer: stay all Swift for now

Do not move the thinking part. Keep one door open: a small TypeScript helper, only for connections, and only if the tools refuse the Swift kit. One short test decides that.

Nothing in the app was changed. The trial lived in a throwaway folder, used a fake model, and made no real call.

What the question really is

TypeScript is not more powerful than Swift as a language. Both can express the same logic. The difference is what already exists around each one.

What Swift has

The Mac itself: reading another app's window, pressing and typing, the Keychain, the microphone and on-device speech, the menu bar, panels that never take focus. None of this exists in TypeScript without native code underneath.

What TypeScript has

Ready-made parts for AI work: the newest kit for connections, browser automation, the official agent kits, and thousands of packages. New helpers appear there first.

So the real question is where the line goes between the two, and whether a second language is worth its cost.

Shape 3 fails on the Mac parts. Nine of Phew's ten Mac needs would still require native code. Electron cannot read another app's controls, and its global shortcut never reports the key being released, so hold-to-talk would not work.

The catch with shape 2

Today "only one function may act" and "the secrets filter runs before every network call" are true because there is one program. Nothing else exists that could go around them.

The internetreached only through Swift

With an engine beside the app, the rules stay true by construction only if the engine cannot reach the network by itself. The trial showed macOS can enforce that.

But an engine with no network cannot run the things TypeScript was wanted for. The connections kit, browser automation and the agent kits all need their own network. So you would choose between the reach and the rules. You cannot have both from the same engine.

The trial, measured

One agent, the research one, was rewritten in TypeScript with the official Claude kit and run beside a small Swift program, talking over a pipe. A scripted fake model stood in for Claude.

What it bought

The official kit's types and request code, and a loop about 15 lines shorter. The gates did stay in Swift: Swift refused a 13th request even when the engine was told it could make 99.

What it cost

An app 30 to 40 times larger, 69 MB more memory, a second language and toolchain, a process that can hang or die, and a network lock that rests on a macOS tool Apple marks as deprecated.

For this one agent, already written and tested in Swift, the move bought almost nothing. It could pay only if many agents or ready-made connectors shared one engine.

What others did

  • Raycast kept a Swift host and added a Node part, for a Windows version and for hiring. Its memory use rose.
  • Codex moved away from TypeScript to drop the Node dependency and to sandbox better.
  • Claude Code is TypeScript, shipped as one program. It is a terminal tool with no Mac interface to drive.
  • No public case was found of a Mac assistant moving to TypeScript to gain reach on the Mac.

The strongest argument against my answer

The gap grows every month. New agent helpers ship for TypeScript and Python first, the Swift connections kit is already one version behind, and an AI coding assistant writes TypeScript agent code more fluently than Swift. Staying in Swift is right today and may stop being right.

How to settle it

  1. Run the test already planned as NB.1. Connect the Swift kit to Notion, then Linear and GitHub.It touches a real service, so it needs your word.
  2. If all three accept it, Swift holds. Connections are built in Swift as planned.
  3. If two or more refuse, build a small TypeScript helper for connections only. Swift still makes every model call and every action.
  4. If a second runtime is ever added, make it a worker with no network for one pure job (read a file, run a self-made skill), not the brain.

Not shown

  • The trial used a fake model, one agent and no real connection.
  • Words appearing live as they are written were not built across the pipe.
  • Signing and notarising an app with Node inside was not tried.
  • Bun and Deno, which make smaller programs than Node, were not installed and not measured.
  • The week counts are estimates.
