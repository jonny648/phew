1. Foundation

1.1 Problem

Students use AI every day and now spend real effort managing it: choosing the tool, explaining the context again, moving text and screenshots, switching apps, deciding between too many options behind a chat box.

One sentence: the AI lives somewhere else and does not know what I am doing.

Numbers from the research:

  • 95% of UK undergraduates use AI. 61% use it to have concepts explained (HEPI 2026, n = 1,054).
  • 85% of US college students used AI for coursework in a year.
  • About 1,200 app toggles a day, about 9% of work time lost reorienting (HBR 2022, n = 137).
  • Productivity rises with up to three AI tools and falls at four or more (BCG 2026, n = 1,488).

Status: desk research only. Validation with users was skipped by your decision on 10 November 2026.

1.2 User

University students, 18 to 26, on a Mac, using AI daily for coursework and their own projects. First user: you.

Job to be done: help me understand and move forward on what is in front of me, without leaving it and without explaining my course again.

1.3 Market

  • Sector: screen-aware desktop AI companions, inside AI assistants and agents.
  • Parent market: AI agents, about $7.6B to $7.8B in 2025, about $50B to $53B by 2030. Mostly enterprise. No credible figure for consumer companions.
  • Screen reading alone became a free macOS feature on 14 September 2026.

1.4 Competitors

Product Overlap What Phew does differently
Clicky Cursor companion that sees the screen and points Phew is silent, lives in the notch, knows your courses, listens to lectures
Littlebird Always-on context and work memory Built for professionals. No guiding on screen, no character
Siri AI On-screen awareness, free No course memory, no guiding, no lecture capture
ChatGPT, Claude, Gemini desktop General help with screen context A chat to manage. Phew removes the chat
MemoryPlugin, Supermemory Shared memory Memory only, no experience

1.5 Position

Clicky for students, built around what they actually do: courses, lectures, assignments, projects. The experience is the product. Memory, context, agents and the Map work underneath and are never the user’s job.

1.6 Risks

  • Scope. This is five products in one. The MVP in 06-sprint.md carries only the main one.
  • Apple, Clicky or Littlebird ships a student version.
  • Trust: screen, microphone and actions in other apps are the three most sensitive permissions on a Mac.
  • Model cost per student against what a student pays.
  • Students rarely pay for tools. See 1.7.
  • The name: check trademark and domain for Phew before public use.

1.7 Who pays

Students and early founders are heavy users and weak payers. As a consumer product this would likely need to be free or open source. The paying versions are business ones, where an organisation buys and an individual uses. See 08-b2b-targets.md.

For now this does not change the build. Phew is a personal tool and a learning project. The student is still the user the MVP is designed for.

2. Vision, mission, values

2.1 Vision

AI help that needs no managing.

2.2 Mission

Help students understand and move forward on what is in front of them, with no chat, no re-explaining and no app to keep open.

2.3 Who Phew is

  • A small black chick, still carrying its eggshell.
  • Shy. He lives in the notch or the menu bar and comes out only when called.
  • Gentle and smooth. He does not really talk. He listens well and shows instead of telling.
  • He understands what you are doing and works on it with you.
  • Tidy. Everything about him is in order: how he appears, moves, and what he keeps.
  • Called Phew!, and he answers to phew, few, phiu, pheoo.
  • Mac only for now. He may decide to come out to other devices later.

2.4 Values as rules

Value Rule for Phew
Familiar Lives where Mac users already look: notch, menu bar, cursor. System shortcuts and gestures
Transparent Everything he knows is visible and editable in the Map on the dashboard. No disclosures during use
Effortless No prompts to write, no project forms, no setup beyond permissions
Consumer value-dense Every feature removes a step the student already takes
Flow-first He never takes keyboard focus. Results arrive at the cursor or wait in the notch
Frontier, where needed Small models and local rules first. Frontier models only for explaining, guiding and acting
Non-intrusive Three parts, below

2.5 Non-intrusive, defined

  1. He does not ruin the experience. He never shows up at random. Self-started work is silent housekeeping only.
  2. He does not ask for many choices. One way in, sensible defaults, no settings needed to start.
  3. He is not intrusive on privacy or data. Private by design: local processing where possible, nothing kept that he does not need. He does not narrate what he is doing every second.

2.6 Feature order

Explaining and guiding is the one visible feature and the output. Everything else serves it.

  1. Explain and guide. Visible.
  2. Context understanding. Underneath.
  3. Memory and the Map. Underneath.
  4. Agent task handoff. Underneath, shown as a pleasant detail.
  5. Lecture listening, actions in other apps, background work. Extensions of 1.

2.7 What Phew is not

  • Not a chat app.
  • Not a talking assistant.
  • Not a tool the student has to manage.

3. Experience

3.1 Three surfaces, one character

Surface Role Behaviour
Notch Home Phew rests here in his shell. Expands slightly to show state and working agents
Menu bar Fallback home and controls Used on Macs without a notch. Holds pause, settings, link to dashboard
On-display presence Explaining and guiding Phew leaves the notch, travels to the spot, becomes a second cursor to point or show, then returns

The on-display presence is the heart of the product. Phew turns into a pointer with a soft effect, indicates an element, underlines, circles or walks through steps, and places a short text card beside it when words are needed. He never speaks aloud.

Difference from Clicky: silent instead of voiced, lives in the notch instead of following the cursor all the time, and the pointer is a temporary form, not his permanent one.

3.3 Ways to call him

All are effortless and none needs a choice.

With nothing said, he explains what is under the cursor. He works on the whole window, a region, a selection or the full screen. Selection is one input among several, not the logic of the product.

3.4 What he does

  • Explain. What is this, in the context of your course.
  • Guide. Shows the next step on screen, one step at a time, in any app.
  • Remember. Learns each time you work on a project. Nothing to save by hand.
  • Hand off. Gives small tasks to agents, such as a short research or collecting sources. Results wait in the notch.
  • Listen to lectures. Captures a lesson and keeps the important details you may miss while writing notes, linked to the course.
  • Act. Takes actions in other apps under the rules in 3.6.
  • Work in the background. When you ask, or on his own for housekeeping.

3.5 Agents in the UI

Agents are visible as a pleasant detail, never as a control panel. Eggs in the notch show how many are working. Hovering shows one line per agent. Full history lives in the dashboard.

4. Architecture

Two views. Section 4.1 is what the MVP builds. Sections 4.2 to 4.7 are the full target, so nothing built now has to be thrown away.

4.1 MVP architecture: everything on the Mac

One Swift app, one repository, no cloud of your own. The only outside call is to the Claude API.

PHEW.APP (Swift, on your Mac)
  Shell     menu bar item, input panel, pointer overlay, text card
  Senses    window text and positions, screenshot, speech to text, secrets filter
  Brain     Conductor, Observer, Guide, Librarian
            behind one interface, so it can move to a backend later
  Map       SQLite file: nodes, edges, events
  Keychain  your Claude API key
        |
        v
  Claude API   small model for Conductor, Observer, Librarian
               main model for Guide

Why local first: no accounts, no servers, no sync, no signing programme. It removes about half of the work and none of the main problem.

The rule that keeps the future open: the Shell and Senses talk to the Brain only through one interface. Moving the Brain to a backend later changes one file.

Running it without the Apple Developer Program: build and run from Xcode, signed with the free personal team of your Apple ID. This keeps the Accessibility and Screen Recording permissions between builds. Verify on day 1.

Positions from the Accessibility API let Phew point at the exact button. When an app exposes nothing, the main model returns coordinates from the screenshot.

4.4 The brain: agents and roles

Agent Job Model MVP
Conductor Understands the request, chooses who works Small Yes
Observer Turns window text and screenshot into a clean context packet Small, with vision Yes
Guide Explains and produces pointing steps. The main agent Main, with vision Yes
Librarian Reads from and writes to the Map Small Yes
Runner Handed-off tasks such as research Main Later
Scribe Lecture transcript to key points Main Later
Hand Actions in other apps Main Later
Keeper Nightly housekeeping of the Map Small Later

Model provider: Claude API. Small means the Haiku class, main means the Sonnet class. The coding agent must read the current model names from the API documentation instead of guessing them.

Flow of one request:

  1. You press the shortcut or hold the key and say “I don’t get this”.
  2. Senses build the raw packet. Observer cleans it.
  3. Librarian adds what the Map knows about this course and topic.
  4. Conductor sends it to Guide.
  5. Guide streams an explanation and steps, each tied to an element on screen.
  6. The pointer shows them.
  7. Librarian records what happened.

Keeping it cheap and quick in the MVP: small model for three of four agents, window text before screenshots, short context packets, streamed answers, cost and latency logged for every call. The wider question of how similar tools do this is a research item in the parking list.

4.5 Backend, later

Part What it does Service
Sign in Accounts, sessions Supabase Auth
Gateway Holds the model keys, checks the user, applies limits Supabase Edge Functions
Background jobs Runner, Scribe, Keeper Trigger.dev
Database Users, the Map, events Supabase Postgres
Vector search Related memories by meaning pgvector
Files Transcripts, exports Supabase Storage
Live updates Eggs, dashboard refresh Supabase Realtime
Website and dashboard Landing, sign in, Map view Next.js on Vercel
Errors and usage Opt in Sentry, PostHog
Payments Stripe

Why Trigger.dev over Inngest: Phew’s background work is agent runs that last minutes. Trigger.dev is built around long-running tasks on its own workers, with a simple task model and an open source licence. Inngest is stronger for many short event-driven steps, which is not Phew’s shape. Not needed for the MVP.

How this backend gets made: you rent four managed pieces and connect them. A database with accounts, small functions that hold the secret keys, a jobs service, a website host. The coding agents write them from this file and 05-map.md.

4.6 Privacy by design

  • Phew reads only when called.
  • Speech is transcribed on the Mac.
  • Password fields are never read. Secrets are removed before any network call.
  • A per-app exclusion list and one pause switch in the menu bar.
  • In the MVP everything except the model call stays on your Mac.
  • macOS shows its own indicators for microphone and screen capture. Phew adds none.
  • Before public release: privacy policy, terms, EU check, recording notice for lectures. Not legal advice.

4.7 Cost

  • MVP: Claude API usage only. No Apple Developer Program, no hosting.
  • Later: the services in 4.5 have free tiers. The Apple Developer Program is needed only to distribute.

5. The Map

Phew’s understanding of meaning, connections and relationships. A light ontology with a small semantic layer on top, taken from your study and cut to what one student needs.

5.1 What was taken from your study, and what was left

Taken Left out
Start from competency questions OWL, RDF, SPARQL, SHACL
Model 5 to 10 core classes Formal reasoning engines
Reuse existing vocabularies before inventing Warehouse tools: dbt, Cube, LookML
Property graph instead of formal logic Modelling everything up front
Define each metric exactly once Enterprise governance
Grow one use case at a time

Your study is sound for this purpose. Two notes: I did not verify its dates, and the Gartner figure of 80% accuracy gain is a forecast, not a measurement.

5.2 Competency questions

The Map exists to answer these. If a class or link does not help answer one, it is not added.

  1. What is this on my screen, in terms of my course?
  2. What have I not understood yet in this course?
  3. Where did the lecturer explain this?
  4. What is due this week, and what does it need?
  5. What did I do last time on this project?
  6. What should I do next?

5.3 Classes

Nine classes. Names follow schema.org where one exists.

Class Meaning Example
Course A subject the student follows Typography 2
Project Own work with a goal Thesis, startup
Assignment Something to deliver Poster brief
Concept An idea to understand Kerning
Source Where knowledge sits Slide deck, PDF, web page, lecture
Lecture A captured lesson. A kind of Source Lesson of 12 November
Person Lecturer, teammate
Session A stretch of work Phew observed 40 minutes in Figma
App A tool in use Figma, Keynote

5.4 Links

Link From, to
part of Assignment to Course, Lecture to Course
covers Source to Concept
requires Assignment to Concept, Concept to Concept
due on Assignment to a date
worked on Session to Project or Assignment
used Session to App
understood, struggled with Student to Concept, with a strength from 0 to 1
taught by Course to Person

Every link stores where it came from, when, and how sure Phew is. This is what lets the student correct him and lets the Keeper clean up.

5.5 Small semantic layer: definitions written once

Term Definition
Due soon Assignment with a due date within 7 days
Untouched Assignment with no Session in the last 5 days
Weak concept Concept with struggle strength above 0.6 and no later success
Covered Concept linked to at least one Lecture or Source of the course
Next step The first required Concept or Assignment that is weak or untouched, ordered by due date

Agents use these terms. None of them invents its own meaning for “due soon”.

5.6 Rules, not reasoning

Three simple rules instead of an inference engine.

  • If an Assignment requires a Concept and the Concept is weak, the Guide starts from that Concept.
  • If a Concept on screen is covered by a Lecture, the Guide points to that moment of the Lecture.
  • If an Assignment is due soon and untouched, it becomes the answer to “what next”. It is never pushed as a popup.

5.7 Three memories

Memory Holds Lives
Working The current task and the last few steps On the Mac, minutes
Episodic Events: what happened, when, in which app Events table, months
Semantic The Map: classes and links Graph tables, permanent

5.8 How it is filled

  1. After each interaction the Librarian receives the context packet and the answer.
  2. A small model extracts items and links, restricted to the classes and links above.
  3. Each item is matched to an existing one or created. In the MVP the small model matches against the names already stored for that course. Embeddings come with the backend.
  4. Links are added with source, time and confidence. Repeated evidence raises confidence.
  5. Later, the Keeper merges duplicates at night, lowers stale confidence and recomputes the terms in 5.5.

5.9 Storage

Four tables. SQLite on the Mac in the MVP, Postgres with the same shape when the backend arrives. The embedding columns stay empty until then.

Table Columns
nodes id, user, class, name, properties, embedding, created, updated
edges id, user, from, to, link, strength, confidence, source event, created
events id, user, time, app, kind, summary, embedding
terms name, definition as a query

5.10 How it grows

MVP: Course, Project, Concept, Source, Session and the links between them, enough for questions 1, 2 and 5. Assignment and due dates next. Lecture when lecture capture works. One use case at a time.

Until the dashboard exists, the Map can be exported to one readable Markdown file. That is the Transparent value in the MVP.

8. Who could pay: business targets

Secondary research, 11 November 2026. A first pass, not a decision.

8.1 The point

Students use Phew and cannot pay. The pattern that works is an organisation that buys and an individual who uses. Explain and guide, in any app, with memory of what the person is learning, is the same product in each case below. Only the content of the Map changes.

8.2 Targets

# Who buys Who uses Why they would pay Evidence Fit now
1 Small Mac-first companies: studios, agencies, startups Juniors, interns, new hires Seniors lose hours showing tools and processes Sits inside the digital adoption market below Best
2 Schools that teach software: design schools, bootcamps, course providers Their students Students stuck in the tool drop out or need tutors No data gathered yet Good
3 Larger companies, training and IT teams Employees learning business software Faster adoption of software they already bought Market about $1.59B in 2026, about $4.37B by 2034, 13.5% a year Weak for now
4 Universities All students Already buying AI for every student See 8.3 Weak for now
5 Software vendors Their customers Fewer support tickets, faster onboarding Existing category, mostly web based Poor

8.3 What the evidence says

Universities do buy AI for students. One US state university system pays $13 million a year to give ChatGPT Edu to about 470,000 students, about $28 per student per year. List prices at another university are $240 to $276 per licence per year. OpenAI is reported to have sold more than 700,000 licences to about 35 public universities. Reading: the budget exists, the unit price at scale is very low, and the competitors are the model labs themselves.

Companies pay for on-screen guidance. Digital adoption platforms, such as WalkMe and Whatfix, overlay step-by-step guidance on business software. The market is put at $1.24B in 2025 and $1.59B in 2026. Their guidance is authored by hand by the customer’s team, and the leaders are now adding AI to write it. Phew’s approach needs no authoring at all. That is the opening.

8.4 Why targets 3 and 4 are weak for now

  • Phew is Mac only. Universities and large companies cannot buy a tool that part of their people cannot run.
  • Both need security reviews, contracts and long buying cycles.
  • Reading employees’ screens raises works council and privacy questions in Europe.

8.5 Recommendation

After the MVP, explore target 1 and target 2 together. They are Mac-heavy, decide fast, and the user is the same young person the product is designed for: a student today, a junior tomorrow.

The nearest test of target 2 is a design school that teaches software-heavy courses. You are inside one.

What changes in the product for a business version: the Map gets shared items written by the organisation, such as “how we set up a file” or “our export settings”, next to the personal ones. Nothing in the MVP blocks this.

8.6 Not yet researched

  • Prices of Clicky, Littlebird and the adoption platforms for small teams.
  • What bootcamps and schools pay today for tutoring and support.
  • Whether small studios feel onboarding as a cost they would pay to reduce. This needs conversations, not search.

9.3 First start, once

  1. Unzip. Move the phew folder where you keep projects.
  2. Open Xcode. New Project, macOS, App. Name: Phew. Interface: SwiftUI. Save it inside the phew folder.
  3. In the project’s Signing settings choose your personal team.
  4. Open Terminal:
cd path/to/phew
git init
git add .
git commit -m "Plan and project skeleton"
claude
  1. First message to Claude Code:
Read CLAUDE.md, roadmap.html and docs/06-sprint.md.
Tell me the current phase and its open tasks. Do not write code yet.

If Claude Code does not see the roles, quit and start claude again.

9.4 Every phase

Start:

Start phase P1. Read the docs listed for it in CLAUDE.md.
Plan the tasks, show me the plan, then use the shell subagent to build.

Finish:

Use the checker subagent to verify every task of P1 against its "done when".
Tick only what passes in roadmap.html, add a line to the log in docs/07-decisions.md, and commit.

Open roadmap.html in the browser and refresh to see progress.

9.5 Two terminals in parallel, optional

P1 with P2, and P4 with P5, do not touch the same files. To run two at once, give the second its own working copy:

When both are verified, ask the lead in the main folder to merge the branch. If this sounds like more trouble than it saves, run the phases one after the other.

9.6 The API key

In P3 Claude Code will ask for a Claude API key. Create it in the Claude Console and paste it only into the prompt Phew shows, which stores it in the Keychain. Never paste it into a file or into the chat with Claude Code.

9.7 Habits

  • One phase per session. Start a fresh session for the next phase.
  • If Claude Code proposes something outside the phase, say “parking list”.
  • When something breaks, describe what you saw. Do not suggest the fix.
  • From P3, use Phew for your own coursework every day.
